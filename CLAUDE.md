# Project: LifeOS — Persian Life Management Platform

A backend-first platform (finance, tasks, habits, Jalali calendar, notes, analytics, AI) where the website is only Client #1. Android, iOS, desktop, Telegram, AI agents, MCP clients, and a public API must all consume the same backend without backend changes. See `~/.claude/plans/7-18-2026-11-25-pm-pouya-async-toast.md` for the original architecture validation and Phase 0/Auth build plan this repo was scaffolded from.

**Delivery sequence: local → git → VPS.** Everything is developed and verified against local Docker first. GitHub push (and CI) comes after local verification passes. Production VPS + Docker deploy (Stage C) has its artifacts written and locally verified as of 2026-07-20 — production Dockerfiles for `apps/web`/`apps/worker`, `docker-compose.prod.yml`, and a `deploy` job in `.github/workflows/ci.yml`. On 2026-07-21 the full production stack (`docker-compose.prod.yml`'s `migrate` profile + `up -d --build`) was smoke-deployed for real against a local Ubuntu 26.04 VirtualBox VM (not a VPS) — proving the whole pipeline end-to-end: real generated secrets, all 5 migrations applied to a genuinely empty Postgres, and a real `request-otp`→`verify-otp` round trip against the containerized standalone app. A real internet-facing VPS is still not provisioned. See `.claude/skills/deployment/SKILL.md` for exactly what's done vs. still blocked on provisioning.

**Architecture Decision Records** live in `docs/decisions/` — the structured "alternatives considered" reasoning behind the biggest calls (monolith vs. separate API, sync-ready vs. offline-first, VPS vs. Vercel, the auth token strategy, the module-resolution fix). This file documents the _what/how_; `docs/decisions/` documents the _why_, with rejected alternatives spelled out. Add a new ADR for any future decision that would be expensive to reverse.

## Architecture Rules (non-negotiable)

1. **No business logic in any client.** Derivation/calculation/aggregation/decisioning happens only in `packages/core`. Clients (web UI, and later Android/Telegram/MCP) fetch data, render UI, send commands. Formatting/presentation (date display, currency display, RTL) is a legitimate client concern; validation logic is shared via `packages/contracts` Zod schemas but the server is the authority.
2. **Single source of truth.** One implementation of every business rule, in `packages/core`. Every client hits the same `/api/v1` contract.
3. **Backend exposes APIs only.** Next.js Server Actions are allowed _only_ as thin adapters calling the same core services (form ergonomics) — never a second logic path. Every capability exposed via a Server Action must also exist as an `/api/v1` route.
4. **Reusable across every future client.** Before writing a feature, ask "can Android use this?" If the answer is no, redesign it.
5. **Modules are isolated** — each owns its API routes, Prisma models, services, and validation (see Finance/Tasks/Habits/etc. in the original spec).

These are enforced **mechanically**, not just by convention — see "Architecture Enforcement" below.

## Architecture Enforcement

`eslint.config.js` at the root defines `boundaries/elements` and `boundaries/element-types` rules (via `eslint-plugin-boundaries` + `eslint-import-resolver-typescript`) that make Rules 1/2/4 a lint failure, not just a convention:

| Element type | Path pattern                 | Allowed to import                                   |
| ------------ | ---------------------------- | --------------------------------------------------- |
| `contracts`  | `packages/contracts/src/**`  | `contracts` only                                    |
| `core`       | `packages/core/src/**`       | `contracts`, `core`, `db`                           |
| `db`         | `packages/db/src/**`         | `contracts`, `db`                                   |
| `web-routes` | `apps/web/src/app/api/**`    | `contracts`, `core`, `web-lib`, `web-routes`        |
| `web-app`    | `apps/web/src/app/**`        | `contracts`, `core`, `web-lib`, `web-app`, `web-ui` |
| `web-ui`     | `apps/web/src/components/**` | `contracts`, `web-ui`                               |
| `web-lib`    | `apps/web/src/lib/**`        | `contracts`, `core`, `web-lib`                      |
| `worker`     | `apps/worker/src/**`         | `contracts`, `core`, `worker`                       |

**Key implication: `apps/web` and `apps/worker` never import `@lifeos/db` directly.** Only `packages/core` does. Each core module that needs the database has one composition-root file (e.g. `packages/core/src/auth/container.ts`) that wires `@lifeos/db` repositories into services and exports ready-to-use singletons (e.g. `authService`). Web/worker import only the singleton. This is what "only core imports db" means in practice — don't add a db-importing helper anywhere under `apps/*`.

Verify the rule is live any time you touch `eslint.config.js`: create a throwaway file under `apps/web/src/components/` that imports `@lifeos/db`, run `npx eslint <file>`, confirm it errors, then delete the file.

## Monorepo Layout

npm workspaces, no Turborepo (kept simple — add it later only if build times demand it):

```
packages/
  contracts/   Zod schemas per module (auth/, common/) — the client contract. Also used for OpenAPI generation later.
  core/        Business logic, services, error hierarchy, logger. Zero Next.js imports. Only place @lifeos/db is imported.
  db/          Prisma schema + generated client + repository classes (each with an I*Repository interface for testability).
apps/
  web/         Next.js 16 App Router — UI + /api/v1/* route handlers (thin controllers only).
  worker/      BullMQ consumers + cron (placeholder — no real jobs yet, see Known Limitations).
```

Within `apps/web/src`:

- `app/[locale]/**` — localized UI pages (fa default, RTL; en secondary).
- `app/api/v1/**` — versioned REST routes, locale-agnostic, Bearer-token authenticated.
- `lib/route-handler.ts` — **`defineRoute()` is how every authenticated route is written** (2026-07-30). A route declares its whole contract — `{ params: ["id"], body: SomeSchema, query: SomeQuery, response: SomeResponse }` — and receives `{ userId, params, body, query, req, requestId }` already authenticated and validated. It **always** authenticates; there is no flag to disable that, which is why "is this route protected?" is answerable by grep. The three genuinely public routes (`request-otp`/`verify-otp`/`refresh`) keep the plain `runRoute` form below.

  This replaced a shallow interface: `runRoute` handed callers `(req, requestId, ctx)` and all 37 route files then re-implemented the same preamble — `requireUser` 34 times, path-param validation 13, `Schema.parse(await req.json())` 29, plus 92 `...(x !== undefined ? {x} : {})` spreads. **That is why one malformed-body bug affected 27 files**: parsing was every route's job. Absorbing those steps deleted `lib/path-params.ts` and `lib/optional-body.ts` outright — each existed only to be called identically everywhere.

  Consequences worth knowing: an **empty body becomes `{}`** so the schema decides whether that's acceptable (a required schema 400s naming its fields, an all-optional one parses — no route needs to know which case it's in); **malformed JSON is a 400**, previously a 500 because `SyntaxError` is neither `AppError` nor `ZodError` and fell through `toErrorEnvelope` to the catch-all; and `params` uses a **`const` type parameter** so `params: ["id"]` infers as a tuple rather than widening to `string[]`, which under `noUncheckedIndexedAccess` would type every segment `string | undefined`. `apps/web/tests/route-auth-coverage.test.ts` asserts the whole contract — including that each route's declared `params` matches the `[segment]` names in its own directory path, and that no route parses its own body.

  **`response` and `query` were added the same week (2026-07-30), and `response` is the one that changed behaviour.** Before it, nothing server-side checked that a route's output matched its own contract — `SignedMoneyAmount` exists because a derived balance could go negative while the schema forbade it, and that surfaced only when a browser parsed a real negative value. Declaring `response` does two separate things: the handler's return type is checked against the contract at **compile** time, and the server `.parse()`es its own output at **runtime**. Three consequences to know:

  - **`NoInfer` on the handler's return type is load-bearing.** `TResponse` appears in two inference positions, so without it TypeScript infers the type from whatever the handler returns and the constraint is satisfied by construction. This was verified, not assumed: before `NoInfer`, a route returning `{ habits: {id}[] }` against `response: HabitListResponse` compiled clean.
  - **A response that fails its own contract is a 500, not a 400.** Letting the `ZodError` propagate would hit `toErrorEnvelope`'s ZodError branch and report a server defect as the caller's mistake — the same inversion C1 fixed in the other direction. It logs `route.response_contract_violation` with the requestId, path, and Zod issues.
  - **The parsed value is what goes on the wire.** Zod strips undeclared keys, so the contract decides the response shape rather than whatever a mapper happened to spread.

  `apps/web/tests/route-contract-coverage.test.ts` is the matching static sweep: every authenticated route declares a `response`, every client `apiFetch` call passes a `schema`, and — the point of it — the route and the client **name the same schema**. Nothing connected those two declarations before; they were written months apart from the same contracts file, by reading.

- `lib/route-handler.ts` — `runRoute()` still wraps every route handler: generates a `requestId`, converts thrown errors via `@lifeos/core`'s `toErrorEnvelope`, forwards a typed `ctx` for dynamic segments. Overloaded to take an optional leading options object (`runRoute({ rateLimit }, handler)`) — the plain `runRoute(handler)` form is unchanged and is what most routes still use.
- `lib/auth-context.ts` — `requireUser(req)` reads the `Authorization: Bearer` header and calls `authService.verifyAccessToken` (core does the actual verification).
- `lib/client-ip.ts` — resolves the client IP for rate limiting, and documents exactly how far it can be trusted (see Known Limitations).
- `next.config.mjs` — the **only** layer that can emit security headers today (`proxy.ts` excludes `/api`, and there's no reverse proxy yet). Its `headers()` covers `/api/v1` too, including `runRoute`'s error envelopes. It also carries the note that the absence of CORS is deliberate (ADR-0019) — that's where someone would go to add it.
- `proxy.ts` — Next.js 16's rename of `middleware.ts`. **Never add a `middleware.ts` alongside it** — Next 16 errors and breaks every build. Currently only runs next-intl's locale middleware; `/api/**` is excluded from its matcher (API auth is Bearer-token, not this gate).

## Module Pattern (established by Auth — copy this for every new module)

1. **Prisma schema**: sync-ready fields on every user-data model — `id` (uuid), `createdAt`, `updatedAt`, `deletedAt` (soft delete), `version`. This is what lets mobile/offline clients add delta sync later with zero backend changes (see "Sync-Ready Convention" below). `AuditLog` is append-only; every mutating service call writes one row.
2. **`packages/db/src/repositories/*.ts`**: one repository class per model, always paired with an `I*Repository` interface. The interface — not the concrete class — is what `packages/core` services depend on in their constructors. This is required for testability: TypeScript classes with `private` fields (e.g. `private readonly prisma`) are nominal, not structural, so a plain in-memory fake object cannot satisfy a concrete-class-typed constructor parameter. It can satisfy an interface.
3. **`packages/core/src/<module>/`**: `services/*.ts` (business rules, constructor-injected repositories), `ports/*.ts` (only for things that genuinely need a swappable adapter — e.g. `SmsProvider` — not for every dependency), `adapters/*.ts` (concrete port implementations, e.g. `MockSmsProvider`), `container.ts` (composition root — the only file that imports `@lifeos/db`). Every service that owns a user-scoped resource with the standard find/ownership-check/mutate/audit-log lifecycle **composes** `packages/core/src/shared/owned-resource-crud.ts`'s `OwnedResourceCrud` (constructor-injected with the repository, `auditLogRepository`, and an `{entityName, actionPrefix}` config) rather than hand-writing that skeleton — see `docs/decisions/0010-owned-resource-crud.md`. It exposes `getOwned`/`audit`/`create`/`update`/`delete`; a service with one divergent step (a different soft-delete method, a repository-level error to translate, an ownership check against a different entity) composes `getOwned`/`audit` directly for that one step instead of the bundled convenience method — see `WalletService`, `BudgetService`, `LabelService`, `ProjectService`, `CalendarEventService`, `HabitService` for the full range of real examples.
4. **`packages/contracts/src/<module>/schemas.ts`**: Zod schemas for every request/response body. Route handlers call `Schema.parse(...)`; `ZodError` is caught centrally by `toErrorEnvelope` in `packages/core/src/http/response.ts` and turned into a `VALIDATION_ERROR` envelope — route handlers never catch `ZodError` themselves.
5. **`apps/web/src/app/api/v1/<module>/**/route.ts`**: thin — parse input via contracts, call the core service singleton, map the returned Prisma model to the contract's response shape (plain field mapping, not a generic serializer), return a plain object (or `NextResponse` for special cases) from the `runRoute()`-wrapped handler.
6. **Tests**: pure unit tests in `packages/core/tests/*.test.ts` using in-memory fakes typed against the `I*Repository` interfaces (see `otp-service.test.ts`, `session-service.test.ts` for the pattern) — fast, no Postgres needed. The full real-DB path is verified by driving the actual HTTP API with curl against the dockerized Postgres (see Verification below) rather than duplicating that as automated integration tests; add real integration tests here if a module's correctness genuinely depends on DB-specific behavior (constraints, transactions) that a fake can't exercise. **`OwnedResourceCrud`'s own ownership-check/soft-delete-exclusion/audit-log behavior is tested once, in `owned-resource-crud.test.ts`** — a new service composing it doesn't need to re-test cross-user rejection or audit-log content itself; its own test file should have only its real domain-logic tests plus one or two smoke tests confirming it's actually wired to `OwnedResourceCrud` (a positive-path create/update/delete via the service, not just via the raw repository fake).

## Auth Module (reference implementation)

- **OTP-first, no passwords — by phone or email.** `POST /api/v1/auth/request-otp` accepts exactly one of `{phone}` or `{email}` (`RequestOtpInput`'s `superRefine` rejects both-or-neither) → 6-digit code (crypto-random via `node:crypto.randomInt`, never `Math.random`), hashed with SHA-256 (namespaced by `channel:identifier:code`) before storage, 5-minute expiry, 60-second resend cooldown, 5 max verify attempts before lockout — all scoped per `(channel, identifier)`, so an SMS cooldown and an email cooldown never interfere with each other. Delivered via `SmsProvider`/`EmailProvider` interfaces — `MockSmsProvider`/`MockEmailProvider` (default, log the code) until real providers (Kavenegar/SMS.ir for SMS; Resend/SES for email) are written; swapping either touches only `packages/core/src/auth/adapters/`. **Logging in by phone once and by email another time creates two separate accounts** — `User.phone`/`User.email` are both optional-but-unique, and there's no identity-linking flow yet (a deliberate scope cut, not an oversight — see `docs/decisions/` if one gets added later).
- **Access tokens are short-lived JWTs** (15 min, HS256 via `jose`, signed with `JWT_ACCESS_SECRET`). **Refresh tokens are opaque random strings** (`crypto.randomBytes(32).toString("base64url")`), never JWTs — only their SHA-256 hash is stored, which is what makes revocation possible (a JWT refresh token can't be invalidated before its own expiry). Refresh rotates the token on every use; reusing an old (rotated-away) refresh token fails immediately.
- **Session revocation takes effect immediately**, not after the access token's 15-minute expiry — `verifyAccessTokenAndSession` checks the session's `revokedAt` in the DB on every request, in addition to the JWT signature/expiry check. This is the deliberate defense-in-depth trade (one extra DB read per request) that makes logout/revoke actually work.
- **`GET/DELETE /api/v1/auth/sessions`** = device management (list + revoke), included from day one per the platform spec's Auth module requirements.
- Env: only `JWT_ACCESS_SECRET` is required (≥32 chars) — refresh tokens need no secret since they're opaque, not signed. Validated lazily via `packages/core/src/config/env.ts`'s `getEnv()` (memoized on first real use, not at import time — keeps unit tests from needing real secrets just to load a module).
- **`verify-otp` returns `isNewUser` (2026-07-29, ADR-0018), and it is the only way any client can tell registration from login.** The route find-or-creates silently, so before this every signup looked identical to a returning login. The flag is computed at the exact find-or-create moment in `OtpService` and passed up through `AuthService` — **do not try to derive it downstream**: a just-created user is indistinguishable from an existing one a moment later, and comparing `createdAt` to "now" is a guess, not a fact. Clients use it to show the name step once; `AuthService` uses it to record a distinct `auth.user.created` audit row **in addition to** `auth.login` (a signup genuinely is both — making them exclusive would put a hole in any "count logins" query).
- **`User.name` is optional permanently, not pending backfill.** An account is created by OTP verification, which only ever knows an identifier, and the name step is skippable — so "account exists" and "account has a name" are independent states and every client must render a fallback. `UpdateProfileInput.name` is `.nullable().optional()`: omitting the key means "leave unchanged", an explicit `null` means "clear it" (the distinction Calendar's `description` still lacks — see Known Limitations). The generated Dart model encodes this correctly, always serializing `name` while omitting plain-optional fields.
- **`DELETE /api/v1/me` is a HARD delete, and deliberately so (2026-07-29).** Every child relation declares `onDelete: Cascade`, so one `prisma.user.delete()` removes all 15 tables' rows — verified against real Postgres in `packages/db/tests/user-repository.test.ts`, which is the assertion actually backing the privacy policy's «حذف کامل». **Do not "improve" this into a soft delete**: `User.deletedAt` exists but _nothing reads it_ — `findById`, the query behind every authenticated request, does not filter on it — so setting it would leave the account fully usable while claiming to be deleted. Sessions cascade away too, which is what revokes access; no explicit revoke pass is needed. The audit row is written **before** the delete (`audit_logs` has no FK to `users`, by design, so it survives) — if the delete succeeded and the audit write then failed, there would be no record of the deletion at all. Requires `{ confirm: true }` (`z.literal(true)`, so `{}` and `{confirm:false}` are 400s); that guards against malformed requests, **not** against a stolen token, which re-authentication would — a separate, larger change.
- **Audit-log metadata stores the MASKED identifier, never the raw one (2026-07-29).** The pino lines always masked it; the stored rows did not, and `audit_logs` is append-only, has no FK to `users`, and has no retention — so a raw phone number written there outlived the account it belonged to, indefinitely. Masked rather than hashed on purpose: an unkeyed hash over ~10⁹ Iranian mobile numbers is a minutes-long rainbow table, and a keyed one needs its own rotatable secret whose rotation silently breaks every historical correlation it existed to provide. Migration `20260729061500_scrub_audit_log_identifiers` strips the key from pre-existing rows (dropping it, not re-masking it in SQL — reimplementing the masking rules in a second language with no test covering them is how you leave more exposed than you intended).
- **Per-IP rate limits are disabled when `DEV_OTP_CODE` is set** (and `NODE_ENV !== "production"`). Not a convenience: every e2e spec runs from one IP, so a single full Playwright run plus any manual curl verification exhausts `otpRequestPerIp` (10/hour) partway through, and four specs fail on a `429` that looks exactly like a regression in whatever they were testing. Raising the number can't fix it — any production-meaningful limit is too low for a repeatedly-run suite. It reuses the existing `DEV_OTP_CODE` dev-mode signal (which already hard-throws under `NODE_ENV=production`) rather than adding a second variable that could disarm production. **Per-identifier cooldowns are unaffected and stay enforced** — they aren't IP-scoped, and they're what actually guards SMS spend.

## Habits Module

- **Streaks are computed on read, never stored** — `packages/core/src/habits/streak.ts`'s `calculateStreak()` walks backward day-by-day from the server's current Jalali day over a habit's non-deleted check-ins, same "derived, never stored" precedent as `WalletService.listWithBalances`'s balance. `DAILY` habits require every calendar day; `WEEKLY` habits only count days in `weekdays` (0=Sunday..6=Saturday, same JS `Date.getDay()` convention as `CalendarEvent.recurrenceByWeekday`) — unscheduled days are skipped without breaking the streak. Today is forgiven (doesn't break the streak) if it's a scheduled day not yet checked, since the user still has until end of day.
- **`HabitCheckIn`'s uniqueness key is `(habitId, jalaliYear, jalaliMonth, jalaliDay)`** — the same precedent `FinanceBudget`'s `(userId, categoryId, jalaliYear, jalaliMonth)` unique constraint already established, extended to day granularity. Un-checking a day soft-deletes the row; re-checking the same day **revives** that same row (an `upsert` that clears `deletedAt`) rather than inserting a duplicate, since the unique constraint is DB-wide regardless of soft-delete state. Verified directly: repeated check-in/uncheck/check-in cycles against real Postgres confirmed via `psql` that exactly one row ever exists per habit per day, with `version` incrementing each time.
- **A client may check in on an explicit past day** (`{jalaliYear, jalaliMonth, jalaliDay}` in the request body, all-or-nothing per `CheckInInput`'s `superRefine`) to backfill a forgotten day from a calendar view — this is ordinary user input (which day happened), not client-computed business logic; the server still owns all streak math. Omitting the date defaults to the server's current Jalali day.
- **Listing N habits costs exactly ONE check-in query, and the window is bounded by `MAX_LOOKBACK_DAYS` (2026-07-29).** `HabitService.withStatusMany` replaced a per-habit `findByHabitId` call that was both N+1 _and_ unbounded — each of the N queries returned the habit's entire lifetime history (≈14,600 rows for 20 habits after two years) to produce 20 integers and 20 booleans, so cost grew with account age and degraded fastest for the most engaged users. `findCheckedDaysForHabits(habitIds, since)` batches via `habitId IN (...)` and narrows with a three-branch `OR` over the Jalali `(year, month, day)` tuple. **The window must be the Jalali tuple, not `checkedAt`** — `checkedAt` stores `now()` even for a backfilled past day (`habit-service.ts`), so a `checkedAt` bound would include rows whose Jalali day is outside the window and exclude ones inside it. Narrowing to `MAX_LOOKBACK_DAYS` is lossless rather than a tolerance: `calculateStreak` provably never walks further back than that, so no excluded row can change any result. Verified at the SQL level (`log_statement='all'`), not just against fakes: 9 habits → exactly one `habit_checkins` statement.
- Routes: `POST/GET /api/v1/habits`, `PATCH/DELETE /api/v1/habits/:id`, `POST/DELETE /api/v1/habits/:id/checkins` (check in / uncheck), `GET /api/v1/habits/:id/checkins?jalaliYear=&jalaliMonth=` (month view).
- **UI (2026-07-22)**: a habit list (`apps/web/src/app/[locale]/(app)/habits/page.tsx`) — each row shows frequency + weekday chips, the derived streak (flame icon, `Habits.streakCount`'s `{count}` pre-formatted via `toPersianDigitsForLocale` for the same reason as Notifications' unread badge), and a one-click "check in today" toggle that omits the date entirely (defaults server-side to today, matching the API's own convention). A collapsible per-habit `HabitMonthGrid` (`_components/habit-month-grid.tsx`) renders the current Jalali month as a Saturday-first 7-column grid via the new `jalaliMonthDays(year, month)` helper (`packages/core/src/shared/jalali.ts`, promoted alongside `jalaliWeekDays`'s existing precedent) — clicking any scheduled day toggles that day's check-in directly (backfilling or undoing a past day), unscheduled `WEEKLY` days render disabled/dim. `updateHabit` was changed to return `HabitWithStatus` (streak + checkedToday) instead of a bare `Habit`, matching `createHabit`/`listHabits`'s shape — the route previously returned a response missing fields `HabitResponse`'s Zod schema requires, which `apiFetch`'s client-side `.parse()` would have caught the moment a UI called it (same class of gap `SignedMoneyAmount` caught for Finance). Habits got its own module accent hue (`--module-habits`, warm red/coral, hue 25) since none of the existing five fit a "streak/fire" association. `apps/web/e2e/habits.spec.ts` covers the full slice: create a DAILY habit → check in today (streak becomes 1) → create a WEEKLY habit with specific weekdays → edit → open the month grid and toggle a day → delete.

## Telemetry Module (2026-07-29, ADR-0017)

Self-hosted crash reporting + analytics on our own `/api/v1`, because ADR-0014's GMS ban rules out Firebase Crashlytics on the exact devices this app targets. `POST /api/v1/telemetry/crashes` and `POST /api/v1/telemetry/events`, both authenticated, both batch.

- **Ingest-only — there is no read side.** No list endpoint, no per-row service method: operators query `telemetry_crashes`/`telemetry_events` directly (psql today, a dashboard once there's a deployed backend). Building a read API before something consumes it is the speculative flexibility ADR-0009/0019 already rejected elsewhere.
- **It is the one mutating service that deliberately writes no audit-log rows.** The audit log records what a _user_ did; a crash is something that happened _to_ them, and a 20-report flush would otherwise write 20 audit rows nobody would ever query.
- **Analytics events are a closed Prisma/Zod enum with no properties bag.** Adding an event costs a migration + a contract change — that's the point (ADR-0017). Anything worth segmenting on becomes its own enum member; a JSON blob would reintroduce exactly the free-form shape the enum exists to prevent.
- **Batch caps in the contract are the abuse control** (20 crashes / 100 events), not rate limiting: Phase 5's limiter is per-IP on _unauthenticated_ routes only, since `runRoute` runs before `requireUser`.
- **`occurredAt` is the on-device instant and is never `createdAt`.** Crashes buffer to disk and flush on the _next_ launch, so reports routinely arrive minutes or days late — ordering or grouping by `createdAt` would cluster every report at flush time.
- **Client-side (`mobile/lib/src/telemetry/`)**: all three error hooks are installed (`FlutterError.onError`, `PlatformDispatcher.instance.onError`, and `runZonedGuarded`'s own handler) because **none subsumes the others** — an unawaited `Future.error` raised inside the zone reaches only the third, verified on a real device. `main.dart` builds an explicit `ProviderContainer` so the hooks, which live outside the widget tree, can reach `TelemetryController`.
- **Opt-out is checked before anything is buffered or queued**, so opting out means nothing is collected at all rather than collected-then-discarded server-side — the stronger claim, and the one the privacy policy makes.
- **Two failure modes worth knowing** (both found on-device, neither catchable by `flutter analyze`/`flutter test`): a `StackTrace` can stringify to **empty**, which fails the contract's `.min(1)` and — since the whole batch is rejected together — poisons every future flush; and a swallowed flush error means such a batch retries forever. `recordCrash` now substitutes a placeholder for a blank trace, and a 4xx (other than 401) drops the batch instead of retrying.
- **Known limitation, deliberate:** a hard native crash or OOM kill takes the process down without either Dart hook running, so it is never captured. That needs a native JNI/NDK handler, out of scope for this module.

## Optimistic Concurrency (2026-07-30, ADR-0020)

`version` used to be incremented by every repository and read by **nothing** — zero `where` clauses referenced it — so two devices editing one row silently lost an edit while the schema advertised sync-readiness. It is now a real precondition.

- **Clients send `expectedVersion` in the request body**, not `If-Match`. A header is HTTP machinery; a body field survives a Telegram/MCP caller (Rule 4) and reaches mobile for free through the Dart generator (ADR-0013), where a header would need hand-written plumbing in all 8 mobile repositories.
- **The comparison lives in the write's own `WHERE` clause and nowhere else.** `packages/db/src/repositories/optimistic-concurrency.ts` provides `versionedWhere`/`runVersionedWrite`; Prisma 6.2.1 permits a non-unique filter alongside the unique one, so it stays one statement that still returns the row. **Never** re-implement this as `getOwned` → compare in JS → `update`: that is check-then-act, both concurrent callers read version 3, both pass, both write. Demonstrated, not theorised — the naive form was run against real Postgres and produced 2/2 successes with the row at version 3, one edit destroyed.
- **`P2025` is ambiguous and is disambiguated on the failure path only** — a re-read decides `VersionConflictError` (row moved) vs `RecordVanishedError` (row gone). Core maps these to `ConflictError` → 409 and `NotFoundError` → 404. Collapsing them makes a sync client retry forever against a deleted row.
- **`packages/core/src/shared/versioned-write.ts` is a free function, not a method**, because `TaskService` predates `OwnedResourceCrud` and has no `crud`. `OwnedResourceCrud.versionedWrite` is a thin binding of it, exposed publicly for the same reason `getOwned`/`audit` are (ADR-0010) — `LabelService.updateLabel` and `ProjectService.deleteProject` bypass the bundled methods and would otherwise leak a raw db error to the route.
- **The field is optional on the wire, and that is a distribution constraint, not indecision.** An installed Cafe Bazaar build cannot be force-updated, so requiring it would 400 every edit on every shipped APK until a store review lands. Absent preconditions emit a `concurrency.unversioned_write` warn; **when that log goes quiet across a release, flip the contract to required** — that is the whole point of the log. Verified live: five versioned writes emitted nothing and a deliberate no-body DELETE emitted exactly one warn.
- **Both clients send it as of 2026-07-30, and each makes it REQUIRED at its own boundary** — `Versioned<T>` in `apps/web/src/lib/api-client.ts`, and a `{required int expectedVersion}` named argument on every mobile repository write. The wire stays permissive for builds already in the wild; new code in either client cannot omit the precondition without failing to compile. That asymmetry is the design, not an inconsistency: permissive where you cannot control the caller, strict where you can.
- **The version a client sends must be the one the user actually saw.** Never re-read the entity just before writing to obtain it — that manufactures a precondition describing a state the user never looked at, which passes the check while defeating its purpose. This is why `CalendarOccurrenceResponse`/`CalendarEventItemResponse` now carry `version` (the agenda row is the only copy of an event a client holds before deleting it), and why `EventFormDialog` uses the version from its per-open fetch rather than a fresh one.
- **`CONFLICT` is three different server conditions and clients must discriminate on `details.currentVersion`** — an optimistic-concurrency failure, an `Idempotency-Key` replayed with a different body (`transaction-service.ts`), and a duplicate label name (`label-service.ts`). Only the first is resolved by "someone else changed this, here is the fresh copy"; saying that about a duplicate label name is simply false. This is the concrete reason the error carries a payload at all rather than a bare 409. Implemented once per client: `use-mutation-error-handler.ts` (web) and `isVersionConflict` in `error_state.dart` (mobile).
- **A rejected write must be visible.** Web routes every mutation's `onError` through `useMutationErrorHandler`, which refetches before showing the message so "try again" is actionable. Mobile had no equivalent — its mutation call sites had no try/catch at all, so an exception escaped into the zone and the user saw _nothing_; `runMutation` (`mobile/lib/src/ui/widgets/run_mutation.dart`) closes that, and callers invalidate unconditionally because a conflict is precisely when the local copy is stale.
- **Not covered:** finance transactions and subtasks (transactions are already guarded by `Idempotency-Key`), and conflict _resolution_ — clients can detect a conflict, not merge one. Mobile also has no habit edit/delete or event-delete UI at all, so those writes exist only on web — a pre-existing parity gap, not something this change introduced.

## Sync-Ready Convention (not full offline-first)

The MVP is server-authoritative and online-first — **not** offline-first (that would put business logic on the client, violating Rule 1, and roughly doubles scope). But every user-data table carries `id`/`createdAt`/`updatedAt`/`deletedAt`/`version` (see `packages/contracts/src/common/sync.ts`'s `SyncFields` schema) so that when Android/iOS eventually need delta sync, it's a matter of adding cursor-based `updatedAt` list endpoints — no schema migration, no backend rework. Mutations on financial data should accept an `Idempotency-Key` header (not yet implemented — add when the Finance module lands).

## Money & Date Conventions (apply when Finance/Calendar modules are built)

- **Money**: `BigInt` minor units in IRR with an explicit `currency` column. Toman↔Rial is a _display-scale_ concern in the presentation layer only — never store or compute in floats, never store Toman as the base unit.
- **Dates**: store `timestamptz` (UTC) everywhere. Jalali/Gregorian conversion happens server-side (`jalaali-js` or `date-fns-jalali`, not yet installed) for aggregation boundaries (monthly budgets, weekly stats starting Saturday) — Jalali month boundaries are business logic, not just display. User profile should carry `timezone` (default `Asia/Tehran`) and a `calendar` preference.

## Module Resolution Gotcha (cross-cutting — read before adding a package)

Every `tsconfig.json` in this repo (base + all packages/apps) uses `"module": "ESNext"` + `"moduleResolution": "bundler"`, **not** `NodeNext`. This was a deliberate fix, not the original choice: `packages/*` were initially `NodeNext` (which requires `.js` extensions on relative imports, e.g. `from "../errors/app-error.js"`, even though the source file is `.ts`). That works fine for standalone `tsc`/`tsx` execution, but **breaks when Next.js/Turbopack bundles the workspace packages' raw TS source** — Turbopack applies `apps/web`'s bundler-resolution rules to everything it processes, including `packages/core`/`db`/`contracts` source files, and bundler resolution doesn't understand the NodeNext `.js`-pointing-at-`.ts` convention. Symptom: `Module not found: Can't resolve './auth/container.js'` even though `container.ts` exists.

**Fix applied**: all packages switched to `bundler` resolution, all relative imports had their `.js` extensions stripped. If you add a new relative import anywhere in `packages/*` or `apps/*`, write it **without** an extension (`from "../errors/app-error"`, not `from "../errors/app-error.js"`). `tsx` and Turbopack both resolve extensionless imports correctly; NodeNext-style `.js` imports will silently work under plain `tsc`/`tsx` but break the Next.js build.

One related non-fatal Turbopack warning you'll see in `next dev` logs: `unexpected export * ... which is a CommonJS module with exports only available at runtime`, referring to `packages/db/generated/prisma/index.js` (Prisma 6.2.1's generated client is CJS). It's a warning, not a build failure — the auth API routes work correctly despite it (verified via the full curl flow). Don't try to silence it by restructuring the `@lifeos/db` barrel export; it's cosmetic.

The first real UI pass (2026-07-20) built the whole styling/data foundation from a bare `apps/web` (no CSS framework, no components — see git history before this date) and shipped it as one full vertical slice: Finance (Dashboard, Wallets, Categories, Transactions, Budgets). Every module now has real UI; the nav's old disabled "Soon" row is gone.

- **A UX pass (2026-07-21) added a Calendar week view, per-module accent colors, and a first-run onboarding tour + per-page help.** Calendar now toggles between the original Agenda list and a Saturday-start weekly grid (`WeekView`, day columns Saturday-first — Saturday renders rightmost under RTL purely from DOM order, no explicit direction handling needed); the view choice persists per-browser via `localStorage` (`lifeos:calendar-view`, presentation-only, not business data). - **Five module accent hues** (`--module-{finance,tasks,calendar,notifications,reports}` + `-foreground`/`-subtle` variants in `globals.css`) replace the previously all-neutral palette (only `destructive`/`income`/`expense` had real hues) — applied to Nav icons/active state, a colored `border-s-4` accent bar on every page's `<h1>`, and Calendar chips colored by source (event/task/holiday) in both views. `apps/web/src/lib/module-colors.ts` is the single place a module's color is decided; don't hardcode a hue inline elsewhere.

- **Tasks' `position`/`beforeId`/`afterId` reordering isn't exposed in the UI** — a deliberate scope cut, not an oversight: `GET /api/v1/tasks` sorts by `updatedAt desc` (for delta-sync consistency), not by `position`, so the list a user actually sees isn't in reorder-able order to begin with. - **`apps/web/src/lib/api-client.ts`'s `apiFetch()` is the only way UI code calls `/api/v1`.** Attaches the Bearer token from `token-store.ts`, retries exactly once through a refresh-token rotation on a 401 (de-duped across concurrent callers), and parses errors into a typed `ApiError` from the same `ErrorEnvelope` schema the server emits. It also `.parse()`s successful responses against the relevant `packages/contracts` Zod schema — real runtime safety, not redundant: this is exactly what caught a real bug (see `SignedMoneyAmount` below) that years of server-only curl-based verification never exercised.
- **`packages/contracts`'s money fields split into two types, not one.** `MoneyAmountInput` (non-negative only) is for anything a client submits (transaction amounts, budget limits — always a magnitude, direction encoded via a separate `type` field) or sums (a budget's `spent`). `SignedMoneyAmount` is for anything **derived by subtraction** that can legitimately go negative — a wallet's or the dashboard's running `balance`, and a budget's `remaining` once overspent. Getting this wrong doesn't fail server-side (nothing there `.parse()`s its own output), only client-side once `apiFetch` validates a real negative value against a schema that forbids it. If you add a new derived/subtractive money field anywhere, reach for `SignedMoneyAmount`, not `MoneyAmountInput`.
- **Never import `@lifeos/core`'s barrel (`from "@lifeos/core"`) from anything that ends up in a client bundle** (`apps/web/src/lib/**` used by `"use client"` pages, or `components/**`). The barrel's `index.ts` re-exports every module's `container.ts`, several of which import `@lifeos/db` → the generated Prisma client → Node's `async_hooks`, which doesn't exist in a browser bundle — breaks with `Module not found: Can't resolve 'async_hooks'`, caught only by actually running the app, not by `tsc`/lint. `packages/core` has no `exports` map, so a deep import bypasses this cleanly: `apps/web/src/lib/format-jalali.ts` imports `getJalaliDateForInstant`/`getJalaliYearMonthForInstant` via `from "@lifeos/core/src/shared/jalali"`, not the barrel — reusing the same pure, fixed-Tehran-offset conversion math the server uses for display formatting, without dragging in anything `@lifeos/db`-adjacent. - **A dialog's "reset form on open" `useEffect` must never depend on a list prop that's recomputed inline on every parent render** (e.g. `categories.filter(...)` with no `useMemo`). Found as a real bug, not a hypothetical: `BudgetFormDialog`/`TransactionFormDialog` depended on `expenseCategories`/`wallets` in their reset effect; any background refetch of that list (e.g. another mutation's broad `["finance"]` cache invalidation) produces a new array reference, re-fires the effect, and silently wipes whatever the user had already typed. - **Font is self-hosted (`next/font/local`, `apps/web/src/lib/fonts.ts`), not `next/font/google`.** Vazirmatn's 4 static weights were copied from the `vazirmatn` npm package into `apps/web/src/assets/fonts/vazirmatn/` at build time — `next/font/google` fetches over the network at build/dev time, and this dev machine has a documented history of unreliable Google-adjacent connectivity (see Environment Constraints above); self-hosting removes that dependency for every environment this ever builds in, not just this one.
- **Data mutations invalidate broadly, not precisely**: any Finance mutation calls `queryClient.invalidateQueries({queryKey: ["finance"]})` — the whole prefix, not a narrow key. Simpler and correct at this data scale (a handful of small per-user lists); revisit only if it becomes a measured performance problem, not preemptively.

## Mobile App (Flutter/Android)

Built 2026-07-25/26 — the second real client, proving the "website is only Client #1" thesis (see the intro). **Full parity with web across all six modules** (Finance, Tasks, Habits, Calendar, Notifications, Reports), verified running end-to-end on an Android emulator (real OTP login via `DEV_OTP_CODE`, real API calls against the same dockerized Postgres, a real wallet created through the app and round-tripped back). See the **`mobile` skill** (`.claude/skills/mobile/SKILL.md`) for the full build/debug playbook — this section is the summary; that skill is the detail, especially for anything Android-toolchain-related.

- **Framework/distribution decisions**: ADR-0012 (Flutter over React Native/native Kotlin/Capacitor), targeting Cafe Bazaar/Myket, not Google Play (GMS is largely unavailable to Iranian users). `mobile/` sits at the repo root, outside the npm workspace globs — it's Dart, not Node.
- **Contract-generation pipeline (ADR-0013)**: Dart can't import `packages/contracts`'s Zod schemas, so `packages/contracts/scripts/generate-dart-models.mjs` walks each schema's runtime shape via Zod v4's own `.def.type` introspection and emits typed Dart models (classes/enums/sealed discriminated unions, with shared fields hoisted onto a union's sealed base as abstract getters) into `mobile/lib/src/generated/`. A custom script, not `openapi-generator-cli` — see the ADR for why. Regenerate with `npm run generate:dart -w @lifeos/contracts` after any contract change; `mobile/test/generated_models_test.dart` round-trips real API-shaped JSON (including the Calendar union) through the generated output to prove the pipeline itself, not just individual endpoints.
- **Architecture mirrors the web's**: per-module `<module>_repository.dart` (thin, no business logic) + `<module>_providers.dart` (Riverpod) + `lib/src/ui/<module>/` screens, same Rule-1 discipline — every derived number (a streak, a budget's remaining amount, a Jalali month boundary) is rendered exactly as the server returned it. `lib/src/shared/format_jalali.dart`/`format_money.dart` port the web's display-only conversions (same fixed `+03:30` Tehran offset, verified against the same Nowruz-1403 reference instant CLAUDE.md documents for the server). `NavigationDrawer` (not a 6-item bottom nav — past Material's recommended max of 5) with the same per-module accent colors as web, converted from the OKLCH tokens in `globals.css` to sRGB (`lib/src/theme/module_colors.dart`).
- **Auth**: `SecureTokenStore` (Android Keystore via `flutter_secure_storage`) vs. `InMemoryTokenStore` (Windows dev builds, test harness), selected by `Platform.isAndroid`. The Dio `AuthInterceptor` is a line-by-line port of the web's `apiFetch` 401-refresh-rotation logic.
- **Push notifications are deliberately not implemented** (ADR-0014) — many Iranian Android devices lack Google Play Services, so FCM is unreliable/absent on the exact devices this app targets (Cafe Bazaar/Myket). The Notifications screen instead polls every 30s via a `Timer.periodic` inside its `AsyncNotifier`, torn down by `autoDispose` when nothing's watching. Do not add a GMS-dependent package without revisiting that ADR.
- **App identity**: `ir.maaleto.app` (renamed from the scaffold's `ir.lifeos.lifeos`), label "مال تو", launcher icon is the landing page's girih 8-pointed-star motif on brand lapis (`assets/icon/`, generated via `flutter_launcher_icons`).
- **Riverpod 3, not Riverpod 2** — real API differences hit building this (documented in full in the `mobile` skill): `WidgetRef`/`Ref` are unrelated types; `AsyncValue.valueOrNull` is now just `.value`; `StateProvider` moved to `package:flutter_riverpod/legacy.dart`; a family `AsyncNotifier` takes its arg via the constructor, not a `build(arg)` override.
- **Android toolchain on this dev machine** is its own can of worms — `dl.google.com`/Android SDK manifests are unreliably blocked (same class as npm's registry block), so `cmdline-tools`, individual `platforms;android-NN`, the NDK, and CMake all had to be hand-downloaded from a Tencent mirror and extracted into place at least once each. JDK needed bumping from the system's 8 to 17 (Microsoft's OpenJDK build). Full recipe, including the exact failure signatures for each gotcha, is in the `mobile` skill — read it before assuming a fresh Gradle failure is a new problem.
- **Not done yet**: iOS (unscaffolded beyond `flutter create`'s default), release signing / Cafe Bazaar+Myket store listings (blocked on Stage C's VPS — a physical device can't reach `localhost`), offline sync (deliberately out of scope, same ADR-0002 rationale as web).

## Testing

No vitest/jest — `node --import tsx --test "tests/**/*.test.ts"` per workspace (root `npm test` fans out via `--workspaces --if-present`). Each package/app's `tsconfig.json` includes `tests/**/*.ts` in addition to `src/**/*.ts` so test files are typechecked too (the `.claude` Stop hook and `npm run typecheck` both catch type errors in tests, not just source).

**Fakes over mocks for core services**: repositories are constructor-injected as their `I*Repository` interface, so tests pass plain in-memory objects (see `packages/core/tests/otp-service.test.ts`/`session-service.test.ts`) — no mocking library, no real Postgres needed for business-rule tests (cooldowns, attempt limits, token rotation, revocation). Type the fake's backing array against the real Prisma model type (`OtpCode[]`, not `any[]`) — ESLint's `@typescript-eslint/no-explicit-any` blocks `any` everywhere, tests included.

**End-to-end verification** for anything DB-dependent is a curl-driven pass against the real dockerized Postgres (`docker compose up -d` → `npm run dev` in `apps/web` → curl the actual routes), not a separate automated integration-test suite — this was how the whole auth flow (request-otp → verify-otp → me → list sessions → revoke → confirm 401 → refresh rotation → confirm old refresh token rejected → confirm `audit_logs` rows) was proven to work end-to-end this session. Re-run that same sequence after changing anything in the auth module.

**`apps/web/tests/route-auth-coverage.test.ts` is a static sweep of the whole `/api/v1` surface**, not a behavioural test, and the distinction is the point. Service-layer ownership is already covered centrally by `owned-resource-crud.test.ts` — but all of that only runs once a route has established _who_ the caller is, and a handler that simply never calls `requireUser` has no failing unit test: the service is never reached with the wrong user, it's reached with no user at all. The test reads every `route.ts` under `src/app/api` and asserts four things: the surface is non-empty (so a broken path can't make the rest vacuously pass), every route mentions `requireUser` except an explicit three-entry `PUBLIC_ROUTES` allowlist (`request-otp`/`verify-otp`/`refresh` — and a public route that _starts_ authenticating also fails, since a stale allowlist is how an unprotected route eventually hides), every public route applies a `rateLimit` (its only possible abuse control), and every `[id]` route uses `uuidParams`. It does **not** prove authorization is correct — a route could call `requireUser` and ignore the returned userId. It catches the realistic failure: a new route file copied from a neighbour with the auth line dropped. A request-level equivalent would be stronger but would live in the Playwright suite, which CI doesn't run; a stronger assertion nobody executes is worth less than a weaker one that always does.

**`packages/db/tests/*.test.ts` is the one real-Postgres integration-test tier** — populated for the first time by `finance-transaction-repository.test.ts` (the `createWithIdempotency`/`updateWithIdempotency` race: two genuinely concurrent calls via `Promise.allSettled`, asserting exactly one row survives) and `habit-checkin-repository.test.ts` (the check-in revive-not-duplicate guarantee, asserted via a raw query bypassing the repository's own `deletedAt` filter). Both are the concrete instance of this section's own "add real integration tests here if a module's correctness genuinely depends on DB-specific behavior a fake can't exercise" carve-out — the equivalent `packages/core` fake-backed tests hand-script the exact collision/upsert behavior being tested here, so they can never disprove it against a real unique constraint. **This makes `packages/db`'s `test` script a real gate, not a no-op** — `.githooks/pre-push` runs `npm test` (fans out to every workspace), so every push now requires Postgres up and migrated locally (`docker compose up -d` first), same as running the app itself already requires. CI runs them too: the `quality` job in `.github/workflows/ci.yml` carries its own `postgres:16-alpine` service + `prisma migrate deploy` step for exactly this reason — "skip CI wiring" was tried first and immediately broke `main`'s CI, because the workspace fanout runs these tests wherever `npm test` runs; there is no local-only mode without gating the test script itself.

## Database (Prisma 6.2.1 + local Docker Postgres)

**Connection**: `DATABASE_URL` env var (`postgresql://lifeos:lifeos_dev@localhost:5432/lifeos` for the docker-compose default). Each workspace that touches Prisma directly needs its own `.env` (Prisma CLI and Next.js both resolve `.env` relative to their own working directory, not the monorepo root) — `packages/db/.env` and `apps/web/.env` both exist and must stay in sync for `DATABASE_URL`.

**Migrations**: `cd packages/db && npx prisma migrate dev --name <description>`. Non-interactive shells can't confirm Prisma's "this looks risky" prompts — if a migration needs confirmation and you're certain it's safe on the (empty, local-only) dev database, use `prisma migrate reset --force` first, then re-run `migrate dev`. Never do this against a database with real data.

**Models** (auth module): `User` (phone-keyed, sync-ready fields), `OtpCode` (phone-keyed, not user-keyed — a phone can request an OTP before any account exists), `Session` (refresh-token-hash-keyed, sync-ready + revocation fields), `AuditLog` (append-only).

## Known Limitations / Deliberate Deferrals

**See `docs/roadmap.md` for the actively-tracked phased plan closing many of the gaps below** (mobile design-system migration completion, dark mode, Redis-backed rate limiting, security headers, a real signup/display-name flow, self-hosted crash reporting — see `docs/decisions/0017`–`0019` for the reasoning behind those choices). This section stays as the point-in-time record of what's deferred and why; the roadmap is where "what's being done about it, in what order" lives.

- **Prisma stayed on 6.2.1**, not upgraded to the offered 7.x — it already works end-to-end (migrations, generation, the full auth flow) and Prisma 7 confirmed requires a driver-adapter pattern (`@prisma/adapter-pg`) plus a generator/output-path rename, not just a version bump. Upgrade deliberately in its own pass, not mid-scaffold, and re-verify the whole auth flow after — concrete step-by-step plan already written: `docs/prisma-7-migration-plan.md`.
- **`apps/worker` is a placeholder** — BullMQ/ioredis are installed but nothing is wired up yet (no real jobs exist until a module needs background processing, e.g. recurring transactions). Its `build` script (`tsc -p tsconfig.json`) emits real `.js` with extensionless relative imports, which **plain Node ESM cannot load directly** (Node's own ESM resolution requires explicit extensions, unlike bundler resolution). Before the worker has real logic and needs a production build, switch its build step to a bundler (`tsup`/`esbuild`) rather than raw `tsc` emit — don't discover this the hard way in a Docker build.
- **i18n now covers every module** (`fa`/`en` routing, RTL, and full message namespaces — `Login`, `Nav`, `FinanceDashboard`, `Wallets`, `Categories`, `Transactions`, `Budgets`, `Tasks`, `Subtasks`, `TaskProjects`, `TaskLabels`, `Calendar`, `Notifications`, `Reports`, `Common`) — extend `apps/web/src/messages/{fa,en}.json` following the existing namespace-per-page pattern for any future module.
- **`CalendarEventUpdateInput.description` has no way to explicitly clear an existing description** — unlike Tasks' `description` (deliberately `.nullable().optional()`, see decision 9 in the Tasks module plan), the Calendar contract's `description` is plain `.optional()` with no `.nullable()` variant, so omitting it means "no change," not "clear it." The Calendar UI's edit dialog reflects this honestly (an emptied description field is simply not sent, leaving the old value in place) rather than papering over it — revisit the contract schema itself if clearing a description turns out to matter.
- **Rate limiting is Redis-backed as of 2026-07-28** (`packages/core/src/rate-limit/`) — closing the two gaps this section previously tracked. A `RateLimitStore` port has Redis (Lua-scripted, atomic) and in-memory adapters; `RateLimitService` owns every decision and **deliberately fails open** when the store is unreachable (a limiter outage must not become an API outage) with a `rate_limit.store_unavailable` warn log; `policies.ts` holds the actual numbers so no client re-decides them. `runRoute` takes an optional leading options argument to apply a limit, and `toErrorEnvelope` derives the `Retry-After` header. Per-IP limits are applied to `request-otp`/`verify-otp`/`refresh` (the unauthenticated routes), **not** as a generic per-user default — `runRoute` runs before `requireUser` so it has no user identity, and a blanket per-IP cap would misfire on shared/NATed IPs. The OTP resend cooldown moved off its read-then-write Postgres race onto an atomic single-slot claim, keeping the old timestamp check only as a fallback for when the store fails open. **`REDIS_URL` unset selects the in-memory store**, which counts per-process — fine for one dev process, but a multi-instance deploy must set it or each instance enforces its own copy of every limit.
- **Misconfiguration fails at startup in production, not at the first affected request (2026-07-29).** `packages/core/src/config/env.ts`'s schema carries a `superRefine` that, when `NODE_ENV === "production"`, requires `REDIS_URL` and `DATABASE_URL` and **rejects `DEV_OTP_CODE` outright**. These are conditional on `NODE_ENV` on purpose: making them unconditional would force every unit test to invent secrets just to import a module, which is exactly what the lazy-memoized `getEnv()` exists to avoid. `REDIS_URL` is the one that matters most at scale — unset selects the in-memory store, which counts per process, so N replicas silently enforce N× every limit; that's not a degraded limiter, it's a wrong one, and it fails silently. A missing `TRUSTED_PROXY_IP_HEADER` in production is a **warn, not an error** — per-IP limits still function best-effort without it (see the next bullet), so failing startup would be disproportionate. `resetEnvCacheForTests()` clears the memo; `packages/core/tests/env.test.ts` covers each branch.
- **Per-IP limits are only as trustworthy as the client-IP source, which today is weak.** `ipAddress` on `Session` was always documented as client-suppliable (`x-forwarded-for`, unvalidated) and display-only — but rate limiting _is_ a security decision input, so `apps/web/src/lib/client-ip.ts` makes the trusted source explicit: `TRUSTED_PROXY_IP_HEADER` names the one header to believe, and when it's unset (today — `docker-compose.prod.yml` publishes port 3000 with no proxy) the limiter falls back to `x-forwarded-for` and per-IP limits are **best-effort**: they stop naive scripted abuse, and a determined attacker rotating the header walks past them. Set that env var to the proxy-injected header (Cloudflare's `cf-connecting-ip`) the moment Stage C puts a proxy in front; only then are these limits real. The per-identifier OTP cooldown, which is not spoofable, is what actually holds the line until then. A global cross-IP OTP cap was considered and rejected — it would cap SMS spend but hand any attacker a trivial way to lock every user out.
- **`ipAddress` on `Session` remains display-only** for the session/device-management UI — never a security decision input, same as before.
- **Web client stores tokens in `localStorage`** (`apps/web/src/lib/token-store.ts`, the single source of truth for this now — used by the login page and every authenticated Finance page's `apiFetch` calls) — necessary for now since the API is Bearer-token-only to stay identical across every client (mobile, Telegram, MCP), but it means an XSS bug on the web app would be able to read tokens directly. It's also why every authenticated page is client-rendered (see "Web UI Architecture" above) — a Server Component can't read `localStorage`. If the web client's XSS surface grows, consider layering an httpOnly-cookie session on top for the web app specifically (a Rule-3-compliant thin adapter) while every other client keeps using raw Bearer tokens.
- **A malformed JSON request body now returns `400`, not `500` (fixed 2026-07-30).** `req.json()` throws a `SyntaxError`, which is neither an `AppError` nor a `ZodError`, so it fell past both branches of `toErrorEnvelope` into the catch-all — a server error for a request that is unambiguously the client's mistake. It affected 29 call sites across 27 files because parsing was every route's own job; `defineRoute` now owns it, and `route-auth-coverage.test.ts` fails if any route reintroduces `req.json()`.
- **The `timezone` setting was removed from both clients (2026-07-29), not fixed.** `User.timezone` was stored and editable in Settings while **nothing read it** — every Jalali boundary in the app uses the hardcoded `+03:30` Tehran offset in `packages/core/src/shared/jalali.ts`, so a user outside Iran could change the control and their "today" would not move. A control that silently does nothing is worse than an absent one: it trains users to distrust settings generally. The column stays (removing it is a migration with no benefit yet); the UI affordance is gone until the boundary helpers actually thread it through. Do not re-add the control without wiring it.
- **SMS provider is mock-only** — logs the OTP code instead of sending it. Real delivery needs a Kavenegar/SMS.ir adapter implementing the existing `SmsProvider` interface; nothing else in the auth module should need to change.
- **No metrics/tracing/alerting infrastructure yet** (OpenTelemetry, Prometheus, etc.) — deliberately deferred, not an oversight. (Mobile crash/usage telemetry _does_ exist as of 2026-07-29 — see the Telemetry Module section — but that is app-level reporting into our own Postgres, not server observability, and it doesn't close this gap.) There's no deployed backend and no metrics/alerting backend to send data to yet (VPS deploy is Stage C), so adding an SDK now would be dead code with no consumer. What exists today: structured pino logs with stable `event` names (`auth.otp.requested`, `auth.login`, `auth.logout`, `auth.session.revoked`, mirroring the audit-log `action` strings) and a `requestId` correlation ID generated per request in `runRoute()`, returned via the `x-request-id` response header, and attached to error logs. Add real tracing/metrics once there's a production target to observe.
- **Notification dispatch (Reports & Notifications module) is synchronous, in-process, and best-effort** — see ADR-0009. Finance's `TransactionService` calls `NotificationService.create()` directly after its own write commits, wrapped in try/catch; a failure is logged and swallowed, never rolled back or retried. This is a deliberate stopgap forced by `apps/worker` still being a placeholder, and it's the template every future cross-module trigger (a Task-deadline reminder, an Auth new-device alert) should copy until the worker is production-ready — don't reach for BullMQ/an outbox table for a single trigger before that's true. `Notification.type` is a plain open string, not a closed enum (ADR-0011) — a future trigger needs zero edits to any Notifications file, just its own local string-literal type (see `FinanceNotificationEventType` in `transaction-service.ts`) for typo-safety at its own call site.

## Secret Hygiene

Same discipline as the sibling `pouyakarimi.ir` project, adapted for local-first development:

- **Secrets are env-only**, read via `process.env.*`. `.env.example` (root) holds variable names with empty values only. Real `.env` files exist per-workspace (`packages/db/.env`, `apps/web/.env`) and are gitignored (`.env*` with `!.env.example` in `.gitignore`).
- **`.githooks/pre-commit`** (installed via the root `package.json` `prepare` script → `git config core.hooksPath .githooks`) runs `lint-staged` (Prettier + `eslint --fix` on staged files) first, then blocks staged `.env`/`*.pem`/`*.key`/`*.local.sql` files and greps the staged diff for common secret token formats. The DSN pattern explicitly excludes `@localhost`/`@127.0.0.1` — the docker-compose dev credential (`lifeos:lifeos_dev@localhost`) legitimately appears in `.env.example` and `CLAUDE.md`, and a localhost-only connection string can never be a real leaked secret. Verified false positive on something else → `git commit --no-verify`.
- **`.githooks/pre-push`** runs the heavier gate before any push: full `lint` → `typecheck` → `test` → `format:check`, then a secret scan across every commit in the push range (diffed against the empty tree for a brand-new branch). Verified false positive → `git push --no-verify` (never to skip a real lint/test/type failure).
- **Claude Code git-guardrails hook** (`.claude/hooks/block-dangerous-git.mjs`, wired as a `PreToolUse` hook on `Bash` in `.claude/settings.json`) blocks Claude itself from running `git push`, `git reset --hard`, `git clean -f(d)`, `git branch -D`, or `git checkout .`/`git restore .` — a second, independent layer on top of the instruction-level git safety rules. Ported from the `git-guardrails-claude-code` skill to plain Node instead of its bundled `jq`-based bash script, since `jq` isn't installed in this environment.
- **The Android release keystore exists as of 2026-07-29 and lives OUTSIDE the repository**, referenced by absolute path from the gitignored `mobile/android/key.properties` — **that file is the single source of truth for where it is, and this document deliberately does not name a path.** It has already moved once (2026-07-30, while being collected for off-machine backup), which broke `flutter build apk --release` with `Keystore file … not found for signing config 'release'` until `key.properties` was repointed. If you hit that error, the keystore moved; fix the path there, not here. 4096-bit RSA, `SHA384withRSA`, alias `maaleto-upload`, `CN=Pouya Karimi, O=Maaleto`, valid to 2053-12-14. Its **SHA-256 certificate fingerprint is `C7:7C:06:EF:81:53:5A:2C:91:5C:DC:43:EF:3B:52:69:A5:17:49:AE:A3:58:5F:13:B3:52:BB:30:53:47:24:8E`** — that value is public (it ships in every signed APK), and recording it here is what lets anyone verify a published artifact came from the right key via `apksigner verify --print-certs`. The path is outside the repo deliberately: `.gitignore` and `.githooks/pre-commit` both already block `*.jks`/`key.properties`, but a key whose loss ends the store listing must not depend on a single ignore rule surviving a future edit. **Losing the keystore or its password is unrecoverable** — Android rejects any update signed with a different key, so the only remedy is a new listing with zero installs, ratings and reviews. Store both in a password manager and one offline copy; a keystore that exists only on this machine is not backed up.
- The repo is pushed to `github.com/Nikosonz/lifeos` (private) and CI is green — "audit history before the first push" is no longer applicable; ongoing hygiene is what `.githooks/pre-push`'s secret scan enforces on every push instead.
